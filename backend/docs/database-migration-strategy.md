# Database Migration Strategy and Rollback Plan

## Overview

This project uses **Prisma Migrations** for schema management. Prisma generates forward-only migrations by default. This document establishes the accepted rollback strategy, emergency procedures, and acceptable data-loss window for this project.

**Key Constraint:** Prisma does not generate down migrations automatically. All down migrations in this project are hand-written and must be maintained alongside forward migrations.

---

## Migration Tools & Commands

| Command | Purpose | Use Case |
|---------|---------|----------|
| `npm run db:migrate` | Apply pending migrations in development | Local development only |
| `npm run db:migrate:deploy` | Apply pending migrations in production (idempotent) | CI/CD pipelines, production deployments |
| `npm run db:migrate:status` | Show migration state and pending migrations | Diagnostics, pre-deployment checks |
| `npm run db:migrate:reset` | ⚠️ DESTRUCTIVE — reset DB and reapply all migrations | **Development only** — destroys all data |
| `npm run db:seed` | Run seed scripts (if configured) | Database seeding after migration |

**Important:** `db:migrate:reset` should NEVER be run against production databases.

## Migration Architecture

### Forward Migrations (Automatic)

All forward migrations are generated by Prisma when the schema is updated:

```bash
# Generate a new migration from schema changes
cd backend
npx prisma migrate dev --name description_of_change
```

This creates:
- `prisma/migrations/[TIMESTAMP]_[name]/migration.sql` — The forward migration

### Down Migrations (Manual)

Down migrations are **hand-written** for reversibility:

```
prisma/migrations/
  20260728000000_add_fraud_alert_model/
    migration.sql    ← Prisma-generated (forward only)
    down.sql         ← Hand-written (reverse operation)
```

**Why hand-written?** Prisma doesn't know your recovery requirements. Down migrations must:
- Be tested and verified
- Include data preservation strategy or explicit data-loss warnings
- Be reviewed as part of PR process
- Have clear documentation about what data is affected

## Rollback Procedures

### Option A: Down Migration (Preferred for Reversible Changes)

**Use this for:** Adding tables, adding nullable columns, creating new features

**Requirements:**
- A corresponding `down.sql` file exists
- The down migration has been tested in staging
- Data loss is acceptable or nil

**Procedure:**

```bash
# 1. Stop application traffic
#    (scale down pods, enable maintenance mode, or pause cron jobs)

# 2. Run the down migration
psql $DATABASE_URL < prisma/migrations/[TIMESTAMP]_[name]/down.sql

# 3. Mark the migration as rolled back in Prisma's tracking table
psql $DATABASE_URL -c "DELETE FROM _prisma_migrations WHERE migration_name = '[TIMESTAMP]_[name]';"

# 4. Verify integrity
npm run db:migrate:status

# 5. Redeploy the previous application version
# 6. Resume application traffic
```

**Example: Rolling back the FraudAlert migration**

```bash
# Stop traffic
psql $DATABASE_URL < backend/prisma/migrations/20260728000000_add_fraud_alert_model/down.sql
psql $DATABASE_URL -c "DELETE FROM _prisma_migrations WHERE migration_name = '20260728000000_add_fraud_alert_model';"
npm run db:migrate:status
# Redeploy v1.0.0
```

### Option B: Restore from Backup (For Destructive Changes)

**Use this for:** Renaming columns, type changes, deleting data, complex rewrites

**Requirements:**
- A recent backup exists and is verified
- Backup is fresher than the incident time
- Data can be restored within RTO/RPO SLA

**Acceptable Data-Loss Window:**
- **RPO (Recovery Point Objective):** 1 hour
- **RTO (Recovery Time Objective):** 15 minutes
- **Backup Retention:** 30 days (rolling)

**Backup Configuration:**

| Environment | Frequency | Retention | Location | Status |
|-------------|-----------|-----------|----------|--------|
| Production | Hourly | 30 days | AWS RDS automated backups + S3 weekly snapshots | Configured |
| Staging | Daily | 7 days | AWS RDS automated backups | Configured |

**Procedure:**

```bash
# 1. Declare incident
#    - Notify on-call engineer
#    - Create incident ticket
#    - Document timeline

# 2. Stop application traffic

# 3. Identify most recent safe backup
aws rds describe-db-snapshots --db-instance-identifier ajo-production-db \
  --filters Name=snapshot-type,Values=automated \
  --query 'DBSnapshots[*].[DBSnapshotIdentifier,SnapshotCreateTime]' \
  --sort-by SnapshotCreateTime

# 4. Restore to point-in-time
# Choose the most recent snapshot before the problematic migration
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier ajo-production-db-restored \
  --db-snapshot-identifier [SNAPSHOT_ID] \
  --publicly-accessible false

# 5. Run connection tests and data integrity checks
npm run test:integration -- --database postgres://[RESTORED_DB]

# 6. Update DATABASE_URL to point to restored instance
export DATABASE_URL="postgres://[RESTORED_DB]:5432/ajo"

# 7. Verify migrations are in consistent state
npm run db:migrate:status

# 8. Run smoke tests
npm run test:e2e -- --smoke-tests

# 9. Resume application traffic

# 10. Clean up old instance after verification (wait 24h first)
aws rds delete-db-instance \
  --db-instance-identifier ajo-production-db-old \
  --skip-final-snapshot
```

### Fraud Detection Tables

**Related Migrations:**
- `20260728000000_add_fraud_alert_model` (FraudAlert table) — ✅ Down migration exists
- Core `FraudFlag` table (created in initial migration) — Part of init

**Down Migration:** `/prisma/migrations/20260728000000_add_fraud_alert_model/down.sql`

**Rollback Risk:** 
- **Data Loss:** All FraudAlert records permanently deleted
- **Severity:** HIGH — Fraud detection history lost
- **Recovery:** Must restore from backup to preserve fraud audit trail
- **Impact:** New fraud alerts can be re-raised after restore

**Procedure:**
```bash

psql $DATABASE_URL -c "DELETE FROM _prisma_migrations WHERE migration_name = '20260728000000_add_fraud_alert_model';"

# See "Option B: Restore from Backup" above
```

## Pre-Migration Checklist

**Before merging any PR that includes a schema migration:**

- [ ] **Schema change reviewed**
  - Does this add, modify, or delete data?
  - Are there backward-compatibility concerns?
  - Has the change been tested against production-like data volume?

- [ ] **Data loss risk assessed**
  - Will this migration lose data?
  - Is that data loss acceptable?
  - Have users been notified (if applicable)?

- [ ] **Down migration exists (if reversible)**
  - Is there a `down.sql` file in the migration folder?
  - Have you tested the down migration in staging?
  - Does the down migration include data-loss warnings?

- [ ] **Alternative: Backup restore documented (if not reversible)**
  - Is a backup available that predates this migration?
  - Have you verified the restore procedure?
  - Are RTO/RPO requirements met?

- [ ] **Migration tested**
  - Has the migration been applied in development?
  - Has the migration been tested in staging with production-like data?
  - Did the migration succeed without errors?
  - Did the application start successfully after migration?

- [ ] **Rollback procedure verified**
  - Have you tested the down migration or backup restore process?
  - Is there a documented runbook for rolling back this migration?
  - Have on-call engineers been briefed?

- [ ] **On-call engineer notified**
  - For high-risk migrations (large tables, data-loss potential)
  - For migrations affecting critical paths (payments, fraud detection)
  - Have they acknowledged and understood the rollback procedure?

- [ ] **PR description includes:**
  - Summary of schema changes
  - Data loss risk (if any)
  - Rollback procedure
  - Link to this strategy document

## Emergency Rollback Runbook

### Incident Declared — Schema Migration Failed

**Timeline:**

| Time | Action |
|------|--------|
| T+0 | Alert fires; incident declared |
| T+2m | On-call engineer notified; incident created |
| T+5m | Root cause identified (bad migration?) |
| T+10m | Rollback decision made |
| T+15m | Rollback procedure initiated |
| T+20m | Application redeployed with previous version |
| T+25m | Smoke tests passing; traffic resumed |
| T+60m | Post-mortem scheduled |

### Runbook

**1. Declare Incident**
```bash
# Create incident ticket
# Notify: On-call engineer, Backend team lead, DevOps team
# Severity: P1 (ongoing issue) or P2 (resolved, post-mortem)

# Gather information
- When did the migration deploy?
- What exactly failed?
- Is production traffic affected?
- Which tables are affected?
```

**2. Assess Rollback Option**
```bash
# Check _prisma_migrations table
psql $DATABASE_URL -c "SELECT migration_name, finished_at FROM _prisma_migrations ORDER BY finished_at DESC LIMIT 5;"

# Determine if down migration exists
ls backend/prisma/migrations/[PROBLEM_MIGRATION_TIMESTAMP]*/down.sql

# If down.sql exists → Use Option A (Down Migration)
# If down.sql missing → Use Option B (Restore from Backup)
```

**3. Execute Rollback**

**For down migrations (Option A):**
```bash
# Stop traffic
kubectl scale deployment ajo-backend --replicas=0

# Run down migration
psql $DATABASE_URL < backend/prisma/migrations/[TIMESTAMP]_[name]/down.sql

# Mark migration as rolled back
psql $DATABASE_URL -c "DELETE FROM _prisma_migrations WHERE migration_name = '[TIMESTAMP]_[name]';"

# Verify
npm run db:migrate:status
```

**For backup restore (Option B):**
```bash
# Stop traffic
kubectl scale deployment ajo-backend --replicas=0

# Identify safe backup (created before migration)
aws rds describe-db-snapshots --query 'DBSnapshots[?SnapshotCreateTime<`2026-07-28T14:00:00`].[DBSnapshotIdentifier,SnapshotCreateTime]'

# Restore from snapshot
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier ajo-production-backup-[TIMESTAMP] \
  --db-snapshot-identifier [SNAPSHOT_ID]

# Wait for restore to complete (~5-10 minutes)
aws rds wait db-instance-available --db-instance-identifier ajo-production-backup-[TIMESTAMP]

# Test connection and data
psql postgres://[RESTORED_DB]:5432/ajo -c "SELECT COUNT(*) FROM _prisma_migrations;"

# Update DATABASE_URL in deployment
kubectl set env deployment/ajo-backend DATABASE_URL="postgres://[RESTORED_DB]:5432/ajo"
```

**4. Restore Application Traffic**
```bash
# Redeploy previous version (without the bad migration)
kubectl set image deployment/ajo-backend app=ajo-backend:v1.x.x-1

# Scale up
kubectl scale deployment ajo-backend --replicas=3

# Wait for readiness
kubectl rollout status deployment/ajo-backend

# Run smoke tests
npm run test:e2e -- --smoke-tests

# Monitor error rates, latency, database connections
# Alert should clear within 2 minutes
```

**5. Verify Integrity**
```bash
# Check application logs
kubectl logs -f deployment/ajo-backend | grep -i error

# Verify database state
psql $DATABASE_URL -c "SELECT COUNT(*) FROM \"User\";"
psql $DATABASE_URL -c "SELECT COUNT(*) FROM \"Group\";"
psql $DATABASE_URL -c "PRAGMA integrity_check;"

# Spot-check user data
psql $DATABASE_URL -c "SELECT id, walletAddress, createdAt FROM \"User\" ORDER BY createdAt DESC LIMIT 5;"
```

**6. Post-Incident**
```bash
# Schedule post-mortem (within 24 hours)
# Document:
#   - What went wrong?
#   - Why wasn't it caught in staging?
#   - How do we prevent this?
#   - Action items & assignees

# Follow-up items
#   - Write down migration (if missing)
#   - Add integration test for migration
#   - Update this runbook
#   - Brief team on incident
```

## Backup Configuration

### Automated Backups

**Production:**
- **Type:** Automated RDS snapshots + hourly WAL backups
- **Frequency:** Hourly automated snapshots
- **Retention:** 30 days (rolling window)
- **Location:** AWS RDS + AWS S3 (weekly exports)
- **RPO:** 1 hour (can restore to any point in last hour)
- **RTO:** 15 minutes (snapshot restore typically 10-15 min)

**Staging:**
- **Type:** Daily automated snapshots
- **Frequency:** Daily at 02:00 UTC
- **Retention:** 7 days
- **Location:** AWS RDS
- **RPO:** 24 hours
- **RTO:** 15 minutes

### Backup Testing

**Weekly Backup Verification:**
```bash
# Run in non-production environment every Monday
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier ajo-backup-test-$(date +%Y%m%d) \
  --db-snapshot-identifier [LATEST_PRODUCTION_SNAPSHOT]

# Run schema validation
npm run db:migrate:status --database postgres://[BACKUP_TEST_DB]

# Run data integrity checks
npm run test:integration -- --database postgres://[BACKUP_TEST_DB]

# Clean up
aws rds delete-db-instance \
  --db-instance-identifier ajo-backup-test-$(date +%Y%m%d) \
  --skip-final-snapshot
```

**Restore Point Recovery Testing:**
```bash

# 4. Document results
```

## Migration Governance

### PR Review Checklist (for reviewers)

When reviewing a PR with schema changes:

```markdown
- [ ] Migration name is descriptive (e.g., `add_fraud_alert_model`)
- [ ] Forward migration is correct (no typos, correct constraints)
- [ ] **Down migration exists** (if reversible changes)
  - [ ] Down migration reverses forward migration exactly
  - [ ] Down migration includes data-loss warnings
  - [ ] Down migration has been tested
- [ ] Data loss documented in PR description
- [ ] Rollback procedure documented
- [ ] Tested in development and staging
- [ ] On-call engineer notified (if high-risk)
- [ ] Link to `docs/database-migration-strategy.md` included
```

### Migration Deployment Process

```
1. PR created with schema changes
2. Reviewer approves (+ checks migration-specific items)
3. PR merged to main branch
4. CI/CD pipeline builds + tests
5. Migration applied to staging environment (for final test)
6. Manual approval for production deployment
7. `prisma migrate deploy` executed in production
8. Post-deployment smoke tests run
9. Monitoring for 24 hours for anomalies
```

## When to Create Down Migrations

**Always create a down migration if:**
- ✅ Adding tables → Drop table
- ✅ Adding nullable columns → Drop column
- ✅ Adding indexes → Drop index
- ✅ Creating new features (separate tables) → Remove feature tables

**Consider backup restore instead if:**
- ❌ Renaming columns (data type mismatch risk)
- ❌ Changing column types (casting failures)
- ❌ Deleting data/columns (permanent loss)
- ❌ Complex data migrations (transformation logic)
- ❌ Large tables (rollback time > RTO)

## Troubleshooting

### Migration Stuck in `_prisma_migrations`

**Problem:** Migration shows as applied but isn't actually (network failure during apply)

**Solution:**
```bash
# Check actual schema (compare schema.prisma)
npm run db:push -- --dry-run

# If schema is correct despite failed migration record:
psql $DATABASE_URL -c "DELETE FROM _prisma_migrations WHERE migration_name = 'PROBLEM_MIGRATION';"

# Re-run migration
npm run db:migrate:deploy

# If schema is incorrect:
# Use down migration to clean up, then re-apply
```

### Corrupted Migration History

**Problem:** Migrations applied out of order or manually altered

**Solution:**
```bash
# Verify current state
npm run db:migrate:status

# Compare actual schema vs schema.prisma
npm run db:push -- --dry-run

# If there's a mismatch:
# 1. Identify where history diverged
# 2. Use backup restore to reset to known good state
# 3. Carefully re-apply migrations in order
```

### Down Migration Not Reversing Everything

**Problem:** Down migration drops table but foreign key constraint fails

**Solution:**
```bash
# Ensure CASCADE constraints are in place
# Add explicit CASCADE to DROP statements if missing:
DROP TABLE "Table" CASCADE;

# Test down migration in development first:
cd backend && npx prisma migrate dev --name test_rollback
# ... verify ...
# Use down.sql to test rollback before deployment
```
